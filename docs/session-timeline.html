Places Nearby Search Cost Spike: Server-Side Proxy, Spend Controls & Beta Gating

A short, design-heavy session with a single commit. It started from a Google Cloud billing notice: Places - Nearby Search had charged $517.41 on the LeadLens project this period (about $219.65 of it from us-west1). The Places APIs were disabled in Cloud Console and all other beta testers were paused while the fix was designed, which means nearby search is currently down on the installed build. Most of the work happened in Google Cloud Console and Supabase rather than the repo.

What was done:

  • Cost scoping — The billing line named Nearby Search specifically, not Place Details. The region split shows roughly $298 came from outside us-west1; that portion has not been attributed to a caller yet (the key's metrics tab and a SKU/region billing report are the next checks).
  • places-proxy Edge Function — Nearby Search now has a server-side path in the LeadLens Supabase project: the Google key never ships in the APK, the field mask is fixed on the server, radius and result count are clamped, and a per-tester daily cap is enforced before any Google call. The function is deployed.
  • Per-tester cap — A places_usage table and an atomic places_take_quota() function (service role only) count every call and still count over-cap attempts. The proxy's first test passed the quota check, confirming the SQL is in place on the LeadLens project.
  • Client wrapper — placesClient.js adds a stable device id, in-memory reuse of the last result for searches under 100 m of movement within 5 minutes, shared in-flight requests, a typed 429 error, and drops permanently closed businesses at the search stage before any Place Details call.
  • Force-update gate & heartbeat — A min-version gate (Scarlett app_config, full-screen prompt, no Modal, fails open) and an hourly tester heartbeat (Scarlett tester_heartbeat via a tester_beat RPC) were written so a build can force testers forward and show who is actually using the app. Both take the Scarlett client as a parameter to keep the two Supabase projects separate.
  • Deploy and test — The first deploy failed because the function file wasn't under supabase/functions/places-proxy/; fixed and redeployed. The first proxy test returned Google's API_KEY_INVALID, so the stored server-key secret is wrong; a direct test of the real key passed authentication and stopped at Places API (New) being disabled in the project.
  • Key plan — Decided the old app key loses both Places entries before Places API (New) is re-enabled, the new server key is restricted to Places API (New) only, the legacy API stays off, and the daily quota is set the moment the API is back on.

Known issues carried forward: Anyone holding the Project Scarlett anon key can currently read every feedback row, including tester name and email — the read policy has not yet been locked down. Manually-created leads (not from a map capture) still default to the old list's first entry, 'HVAC / Mechanical', on a blank start — flagged twice on Sep 28, not yet acted on. Stage 2 of the taxonomy migration beyond capture (exports, dashboards, the web portal) has not started. Not yet field-verified: bulk address import (route/opportunity), the Google Drive image picker, and a second PDF territory pass. Five EXPO_PUBLIC_ env vars the app reads (Google/OneDrive OAuth client values, enrichment provider) are not set in .env; an unused EXPO_PUBLIC_ANTHROPIC_API_KEY line should be removed. New this session: nearby search is down on the installed build until Places API (New) is re-enabled with a daily quota and a build wires in the proxy; the GOOGLE_PLACES_SERVER_KEY secret needs resetting (the proxy returns API_KEY_INVALID); the old app key still needs Places removed from its restrictions first; the Scarlett SQL (app_config, tester_heartbeat) is not confirmed run; the proxy, client wrapper and both hooks are committed but not wired into the app.
